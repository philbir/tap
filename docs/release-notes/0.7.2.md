# Tap 0.7.2 Release Notes

A Studio release about one thing seen from four angles: getting a value out of the field you
typed it into and into the place it belongs — then finding it again afterwards.

## Convert to variable

Any field that takes a token now offers **Convert to variable** while it holds a plain literal.
The panel asks two questions, and they are deliberately not the same question:

- **Where is it declared** picks the cascade tier — workspace, collection, environment, or the
  request itself — and names the file the entry will land in *before* you commit to it. That
  choice is what decides who else can spell `{{name}}`.
- **Is it secret** decides whether the value may sit in that file at all. A secret goes to a
  writable provider instead, and the declaration keeps a `{{provider:key}}` reference in its
  place — so the `secret: true` flag and the file on disk agree about what is where.

Either way the field itself ends up with the bare `{{name}}`. That indirection is the point of
declaring rather than referencing a provider directly: the request reads the same in every
environment, and repointing it at another vault is one line in one file rather than an edit to
every field that spelled the secret out.

Three things it is careful about:

- **Only the entry is written.** The rest of the target file — including its comments — is left
  exactly as it was. Full spec saves still re-emit canonical YAML; this write patches one key
  through a new read seam (`WorkspaceFileText`) rather than round-tripping the document.
- **The secret reaches its provider first, then the declaration referencing it.** Reversed, a
  failure between the two writes would commit a workspace file pointing at a secret that was
  never stored. This way the worst case is an orphaned provider entry, which resolves fine and
  is overwritten by the next attempt.
- **An editor already open on that file does not undo it.** The declaration lands on disk while
  that editor may be holding an unsaved draft that predates it; the draft has to win over the
  reloaded file, but it knows nothing of the new entry. Declarations are now recorded per tab
  and folded in on every re-seed, so the order the two happen in stops mattering.

## Find in a response

`Ctrl/Cmd+F` — or the magnifier in the response header — opens a find bar that applies to
whichever response tab you are on. A response is the thing you actually came to read, and until
now the only way through a 400 KB body was the scrollbar.

The panel is not one view, so the bar means two things and says which:

- **Body** and **Request** are documents you navigate. `Enter` / `Shift+Enter` step through
  matches and the counter reads `3/74`. Matches are computed against what the editor is
  actually showing, so they land correctly in pretty-printed JSON.
- **Events**, **Frames**, **Headers**, and **Cookies** are lists you filter. Matching rows stay,
  the rest go, and the readout says `12 of 40`. Sequence numbers are preserved, so a filtered
  stream still tells you where you are in it.

Case sensitivity and regular expressions are toggles; in regex mode `^` and `$` anchor to lines,
which is what anchoring a search inside a document normally means. The query follows you across
tabs and survives a re-send — "watch this field on every run" is typed once.

## A name filter for Key Vault providers

A team vault usually holds far more than one workspace needs. `azkv` providers take an optional
`filter` — a regular expression over the secret's name:

```yaml
- name: kv-billing
  type: azkv
  settings:
    vaultName: acme-prod
    filter: '^billing-'
```

It is matched against the name as tokens spell it (after any `prefix` is stripped) and is
**unanchored**, so `billing` matches anywhere while `^billing-` matches only at the start —
what a regex normally means, rather than a silently anchored one.

It is a scope, not a display convenience. A name outside the filter is absent from listings and
from Browse, resolves as a miss (`{{kv-billing:payments-key}}` fails as unknown rather than
reaching past the filter), and **refuses writes** — storing a secret the provider would then
hide is worse than being told no. An unparseable pattern is `E_PROVIDER_CONFIG_INVALID`.

## The file provider says where it lives

The `file` provider had no settings and therefore nothing on screen answering "where do my
variables actually end up?".

- **Manage names the file.** The header reads `Encrypted file · workspace scope ·
  .vars/<name>.yml`, and one click copies the absolute path — the thing you need when the
  question is what to back up or what you just committed. The provider card in Settings and in
  the workspace editor names it too, instead of only saying it has no settings.
- **Manage gained a Source tab.** The whole store, as it is on disk, beside the variable table
  — for the edits a row-at-a-time table is the wrong shape for: renaming several keys, pasting
  a store from another machine, or reading what is actually in the repo. Same editor every
  other Source tab uses.
- **The provider validates before it writes.** A store it could not read back never reaches
  disk: bad YAML, a `variables:` block that isn't a mapping, an unknown key, a missing `value:`
  — and notably a `secret: true` whose value is not an `enc:v1:…` envelope, which would be
  clear text sitting under a flag claiming otherwise. Errors come back on the offending line
  and the file is left untouched. Secrets are still encrypted by setting them in the table.

The docs said this store lived at `.tap/.vars/<name>.yml`. It is `<workspace>/.vars/<name>.yml`,
and now that the path is on screen the prose says the same thing.

## Upgrading

Nothing to migrate. No workspace-format, CLI, or API breaking changes — the `azkv` `filter`
setting is new and optional, and a workspace that doesn't set it behaves exactly as before.
`.md` workspace files still load with a `W_LEGACY_EXTENSION` warning for the whole 0.7.x line;
`tap-studio migrate` converts a workspace when you're ready. Removal is still targeted at 0.8.0.
