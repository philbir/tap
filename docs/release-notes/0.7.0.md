# Tap 0.7.0 Release Notes

## Workspace files are now `.tap`

Tap workspace files carried a `.md` extension from the beginning. It bought real things — every
editor highlighted the frontmatter, the fenced `http` block, and the prose around them for free —
but it also meant a repo full of Tap files looked like a repo full of documentation. `orders.req.md`
gave no hint that it was executable, and a manifest called `tap.md` read like a note about Tap.

From 0.7.0 the canonical extension is `.tap`:

| | 0.7.0 | Before |
|---|---|---|
| Manifest | `workspace.tap` | `tap.md` |
| Collection | `_collection.tap` | `_collection.md` |
| Request | `orders.req.tap` | `orders.req.md` |
| Auth · env · flow · test | `*.auth.tap` · `*.env.tap` · `*.flow.tap` · `*.test.tap` | `*.auth.md` · … |

**The format itself did not change.** Same YAML frontmatter, same markdown body, same fenced `http`
blocks, same rule that the filename suffix is canonical and `kind:` must agree with it. A migrated
file differs from its predecessor only in its name.

### Nothing breaks today

Both families load for the whole 0.7.x line.

- A legacy `.md` workspace loads exactly as before. Each file reports a `W_LEGACY_EXTENSION`
  **warning** — a new severity tier, so this does *not* fail `tap-studio lint` and will not turn
  your CI red.
- New files are always written as `.tap`. An existing `.md` file that you edit and save is written
  back *in place*, never quietly renamed: renaming it as a side effect of clicking Save would
  orphan every reference pointing at it.

Support for `.md` workspace files is scheduled for removal in **0.8.0**.

### Migrating: one command

```bash
tap-studio migrate --dry-run   # review the plan
tap-studio migrate             # rename files and rewrite refs together
```

The rename is the easy half. The half that matters is that a cross-file reference is a literal
relative path carrying an extension — `auth: ../../auth/admin.auth.md`, `request: ./orders.req.md` —
so renaming a file breaks every ref aimed at it. `migrate` does both in one pass, covering request
`auth:`, collection `defaultAuth:` (top level and per stage), manifest `defaultEnv:`, flow step
`request:`, and test entry `request:`/`flow:`. Refs written as `id:` need no rewriting and are left
untouched.

Some deliberate properties:

- **It refuses to run on a workspace that doesn't parse.** Migrating broken refs would compound the
  problem rather than fix it.
- **It plans before it writes.** Collisions and unreadable files are found up front, and
  `--dry-run` prints the whole plan — every rename, and every ref rewrite with its line number.
- **It doesn't reformat your files.** Refs are rewritten textually inside the frontmatter block, so
  key order, comments, quoting style, indentation, and CRLF line endings all survive. Each ref keeps
  the shape you wrote it in (`./x`, `../../x`, quoted or bare). The diff is the rename plus the
  changed path segments, nothing else.
- **It's idempotent.** Running it on a migrated workspace is a no-op, so it's safe in a script.
- **It verifies.** After writing, the workspace is re-loaded from disk and the command exits nonzero
  with restore guidance if anything fails to resolve.

Renames are plain filesystem moves; `git add -A` picks them up as moves.

### Also in this release

- **OpenAPI import.** Point a collection at an OpenAPI description — upload a file or fetch a URL —
  and pick which operations become requests, as either one `.req.tap` per operation or one `.http`
  file per tag. `servers[]` becomes the `baseUrl` and stages, `securitySchemes` becomes an auth
  profile wired to variables, and request schemas become example bodies. JSON or YAML; 3.0, 3.1,
  and Swagger 2.0.
- **Re-sync.** An import stays linked to its document (`_openapi.lock.json`). Re-sync re-fetches,
  diffs, and shows what was added, changed or removed — defaulting to keeping your version wherever
  you have edited a request. Applying an update rewrites only the fields the importer owns, so
  assertions, variables and auth survive by construction. Operations dropped upstream are tagged
  `deprecated`, never deleted.
- **`AddTapStudio().WithApi(api)` scaffolds from OpenAPI.** On first run the Studio fetches the
  API's `/openapi/v1.json` (the ASP.NET Core default — override with `openApi:`) and generates a
  request per operation instead of a placeholder. The collection's `baseUrl` stays
  `{{aspire:<name>}}` so it follows the port Aspire allocates. Additive and first-run only; an
  unreachable API just leaves the starter request in place.

- **Warning severity for workspace problems.** `WorkspaceError` now carries `Severity`
  (`error` | `warning`). `lint` reports both but only errors set the exit code, and repeated
  warnings collapse to one line plus a count (`-v` lists them all) so they can't bury a real error.
  Studio shows warnings in yellow, distinct from errors.
- **`E_EXTENSION_COLLISION`.** If both `orders.req.md` and `orders.req.tap` exist — what a
  half-finished migration leaves behind — the canonical file wins deterministically and the leftover
  is reported instead of silently doubling the request.
- **Workspace detection accepts either manifest name**, so an unmigrated workspace is still
  discoverable by the CLI's upward and downward search — otherwise `migrate` itself would be
  unreachable from inside the workspace that needs it.

## Secrets: one machine key, and marks that mean something

Two things about secret handling didn't hold up.

**`secret: true` didn't move the secret.** Marking a variable secret in a collection, request, or
env masked it in the UI and redacted it from anything echoed to an agent — and left the literal
value sitting in the workspace file, in clear text, on its way into Git. The mark said one thing
and the repository said another.

Marking a variable secret in Studio now moves the value. It is written to a writable provider, and
the file keeps a reference where the literal used to be:

```yaml
vars:
  stripe.key:
    default: '{{file:stripe.key}}'
    secret: true
```

You choose the provider and the name it takes there; the dialog shows the exact token before it
writes anything, and "keep it in the file" stays available for values that are only sensitive by
courtesy.

**A declared variable may now hold a token.** That sentence used to read "nothing downstream
changes — resolving that token is ordinary variable resolution", and it wasn't true: expansion
was single-pass, so a variable whose value was `{{file:stripe.key}}` went out on the wire as
exactly that string. Marking a variable secret quietly broke every request that read it, in the
Studio and in `tap-studio` alike. A `{{name}}` that hits a variable a `vars:` block declared now
expands that variable's value in turn — through the whole chain, wherever a `vars:` block can be
written: the manifest, a collection, a stage, an env, a request, a `.http` file's `@name` lines,
and a test set's or flow's own variables.

The line it does not cross is what a run produced. A value a flow step bound with `extract:`, a
`--var` the caller typed, and whatever a provider returned are all emitted verbatim however
token-shaped they look — re-scanning a response would let the upstream pick which secret the next
request carries. A chain that closes on itself now fails with `E_VAR_CYCLE` naming the loop
instead of being impossible by construction.

**The encryption passphrase was a property of the `file` provider.** Which meant it could be
declared in `workspace.tap`, next to the ciphertext it unlocks, in the same commit. It is now a
property of the *machine*, resolved in one order and configurable nowhere else:

| Source | |
|---|---|
| `TAP_ENCRYPTION_KEY` | Wins outright. How CI supplies it. |
| `<system-dir>/encryption.key` | `$TAP_SYSTEM_DIR`, else `~/.tap`. Written owner-only. |

The key file provisions itself: storing a secret on a machine that has none generates it first, so
there is no setup step before the first secret. Only the write path does this — a secret *read*
with no key still reports the ciphertext as unreadable rather than handing you a fresh key that
cannot read it either — and an exported `TAP_ENCRYPTION_KEY` suppresses it, since a key file the
variable shadows is one nothing reads.

```bash
tap-studio key status   # is there a key, and where from
tap-studio key init     # generate one up front; refuses to overwrite an existing key
```

`key init` is for provisioning and backing the key up before there is anything to lose, and for
`--force` rotation; Studio offers the same step inline. The name is deliberately generic: the next
thing that needs at-rest encryption should not invent a second key.

### Breaking

- **`TAP_FILE_PROVIDER_KEY` and `TAP_FILE_PROVIDER_KEY_<NAME>` no longer have any effect.** Export
  the same passphrase as `TAP_ENCRYPTION_KEY`, or write it to `<system-dir>/encryption.key`, and
  existing stores decrypt unchanged — the key derivation did not change, only where the passphrase
  is read from.
- **The `file` provider's `encryptionKey` setting is gone.** If you had one in `workspace.tap` or
  `system.json`, move that same string to one of the two sources above before upgrading. Left in
  place it is ignored, and secret values read as `E_PROVIDER_DECRYPT_FAILED`.

## Variable providers have an editor

A provider's contents were readable (the Browse drawer) but not editable — the file provider, whose
whole point is being the writable one, had no way to add a variable to it short of the API.

Read/write providers now open as their own editor tab: add, rename, delete, reveal, and flip a value
between plain and encrypted, with the same draft-and-save model as every other editor. Flipping a
stored value to secret never round-trips its clear text through the browser — the server re-reads
what it already holds and rewrites it encrypted. Read-only providers open too, and say so.

`IVariableProvider` gained `DeleteAsync`, which is a breaking change for any out-of-tree
implementation.

## Large responses: the rest of the body is one click away

A response over 2 MiB was cut to its first 2 MiB and the remainder was dropped on the floor. The
body pane said `[…truncated; 12,884,901 more bytes follow]`, Download saved that same truncated
text, and the only way to see the rest was to send the request again — which, for a POST that
charges a card or a GET whose report is generated fresh each time, is not a way at all.

The cap is still there, and still small on purpose: a 200 MB payload in a code editor is a frozen
tab. What changed is that the bytes past it are no longer gone.

- **Show all.** The truncation banner now says how much you're looking at and how much there is,
  and offers to render the rest — up to what the host retained.
- **Download gets the whole response.** It streams the retained copy straight from the server to
  disk rather than saving the prefix the panel rendered. Nothing is re-sent, and nothing is
  buffered into the page on the way through.
- **Both caps are yours to set**, in `workspace.tap`:

  ```yaml
  response:
    maxBytes: 8mb           # what reaches the panel and the assertions
    maxRetainedBytes: 256mb # what stays reachable behind Show all / Download
  ```

  Sizes take a `kb`/`mb`/`gb` suffix or a plain byte count. Defaults are 2 MiB and 64 MiB; the
  Workspace editor's General tab has both fields.

`response.maxBytes` is also the cap body assertions see, so a workspace whose payloads are
routinely larger than 2 MiB can now raise it and have `jsonpath` assertions evaluate instead of
reporting *body truncated*. The retained copy is deliberately not part of that: it lives in a temp
directory for the last few responses and is deleted when Studio exits — it is there so you can read
what came back, not so a test can quietly assert against 200 MB.

## Request history

Until now, a response existed only while you were looking at it. Close the panel, send something
else, switch tabs — gone. The only way back was to send the request again, which for anything
that charges a card or writes a row is not an option, and which anyway tells you what the endpoint
does *now*, not what it did when it broke.

Turn history on and every exchange the Studio sends is written to `.tap-history/` at the workspace
root:

```yaml
# workspace.tap, _collection.tap, or a single *.req.tap
history: true

history:                   # or the long form
  enabled: true
  maxEntries: 25           # per request, oldest pruned
  encrypt: false
  maxBodyBytes: 256kb
  orphanRetentionDays: 30  # workspace.tap only
```

It is **off by default**, and the three scopes merge **per key** with the nearest winning — so a
collection can record everything under it while one chatty request sets `history: false` or a
smaller `maxEntries` without restating the rest. There are two ways to read it back: a **History**
tab on each request, and a workspace-wide **timeline** in the sidebar, filterable by collection and
outcome. Picking an entry renders it in the normal response panel, marked *from history* so a body
from Tuesday is never mistaken for the one you just got.

### Secrets: masked, or encrypted — never neither

A recorded exchange is either redacted and plaintext, or unredacted and encrypted. There is no
third combination.

By default the same redactor that scrubs the CLI's `--json` and the MCP results runs over every
entry: `Authorization`, `Cookie` and friends are masked by name, and every resolved secret is
replaced by value wherever it landed — the URL, the request body, the response, even an assertion's
failure message.

`encrypt: true` trades that for the thing masking can never give you — what actually went on the
wire — by sealing the whole entry in the same AES-256-GCM envelope the `file` variable provider
uses, under the machine key (§12.5). If that key can't be obtained, **nothing is written**: a
silent downgrade to plaintext would spill credentials in exactly the configuration that asked for
the opposite.

The folder writes its own `.gitignore` on first use, so none of this reaches a commit because
somebody forgot a line in the repo's ignore file.

### Every file now gets a stable `id:`

The format has always specified one — "auto-generated as a UUIDv7 on first save if omitted" — but
nothing except the OpenAPI importer ever minted it, which left `id:` references theoretical. The
Studio now assigns an id to every file it writes, at creation rather than at some later save, so a
request created and sent in the same breath already has an identity.

History keys on that id, which is what makes it survive a rename: move the file, rename the
request, and its recorded exchanges follow. Delete the request and its history becomes an
*orphan* — still readable (each entry records the name and path it had at the time), tagged in the
timeline, swept after `orphanRetentionDays`, and **re-linked automatically** if a file with that id
comes back from a revert or a branch switch.

A request with no `id:` is not recorded, and the History tab says so rather than showing an empty
list. Hand-written workspaces pick one up on their first save through the Studio.

Only the Studio's interactive **Send** records today. `tap-studio send`, the MCP tools, and test
runs deliberately do not.
