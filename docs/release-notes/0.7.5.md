# Tap 0.7.5 Release Notes

A release about the one failure Studio could not talk its way out of: the desktop app
starting up, and then showing you nothing at all.

## The white screen

The shell has had a splash that narrates startup since 0.7.1 — it names the phase it is in,
shows the sidecar's own progress messages, and turns into a failure card with the log tail
when a launch goes wrong. All of that works, and none of it helped, because it is only on
screen until the shell navigates the window at the backend. Navigating is a one-way door: it
replaces the splash, and with it the only surface that can explain anything. Every failure on
the far side of that door — and there are several — was a white window with nothing in it, no
way back, and nothing written down.

Worse, the shell already knew about one of them. When it could not find the bundled UI files
inside its own resources it logged `WARNING could not resolve the wwwroot resource — the UI
will be blank` and launched anyway, into the blank window it had just predicted.

Three guards now close that door, and all of them end at the failure card that was already
there:

- **The sidecar will not say it is ready unless it can actually serve the UI.**
  `studio.ready` meant "Kestrel bound a port", which is not the same claim: an install whose
  `wwwroot` never arrived binds happily and then answers `/` with a bare 404. Studio now checks
  for `index.html` under the resolved web root first and reports `webroot.missing` /
  `webroot.empty` on the handshake instead, naming the exact path it looked at. The shell,
  likewise, refuses to launch at all when it cannot resolve its `binaries/wwwroot` resource.

- **The shell looks through the door before walking through it.** One loopback GET for the page
  it is about to load, retried for six seconds, which has to come back 2xx with a non-empty
  body. A refused connection, a 404, or an empty document becomes a failure card quoting the
  status line rather than a window that goes blank. Every resolved address is tried, not just
  the first — on Windows `localhost` resolves to `::1` ahead of `127.0.0.1`, and giving up on
  the first refusal would report a perfectly live server as dead.

- **The page watches itself once it has loaded.** A document that parses, answers 200, and
  *then* renders nothing — a bundle whose top-level code throws, a WebView2 too old for the
  syntax the build emitted — is the one white screen no server-side check can catch. The shell
  injects a watchdog that records what the page's own error handlers see and, if the app has
  still painted nothing by the deadline, hands the window back to the splash with the reason
  attached. What you get is the actual error and the file and line it came from, instead of
  white.

It reports back by navigating rather than through a new command, deliberately. The workbench
origin can already navigate itself anywhere; a command would have had to be granted to
`remote.urls`, which would make it reachable by anything that injects script into the page you
point at other people's APIs.

A sidecar that dies *after* the handover is recovered the same way: the window comes back to
the splash with the exit code, rather than sitting on a page whose backend has gone.

The startup log now opens with the two facts any blank-page report has to start from — the
webview runtime version and the resolved `wwwroot` path — and records every navigation the
webview makes. On Windows it is at
`%LOCALAPPDATA%\dev.philbir.tap-studio\logs\studio.log`; on macOS,
`~/Library/Logs/dev.philbir.tap-studio/studio.log`. The previous session is kept beside it as
`studio.prev.log`.

The splash itself is now hardened against its own failures, which matters more than it sounds:
a splash that breaks silently turns every backend failure back into the white screen it exists
to replace.

`TAP_STUDIO_BLANK_TIMEOUT_SECS` sets the blank-page deadline (default 12 seconds; `0` disables
the watchdog) for anyone deliberately staring at a slow first render.

**This is a diagnostics release, not a diagnosis.** It does not claim to fix the underlying
cause of any particular blank window — it makes the app say which of the several possible
causes it hit, which it previously could not do at all.

## Request bar, variables, and the TLS report

Shipped alongside:

- **The method picker** is narrower, sized to the widest verb rather than the widest verb plus
  slack, since the URL is the field that wants the room — and is coloured per verb in both the
  input and the dropdown. Three near-copies of the colour table already existed and had drifted
  apart, so they now read one table; `HEAD` and `PATCH` change colour in the `.http` editor as
  a result, which is the point. Its own comment claimed it matched the request list, and it
  didn't.

- **Provider-qualified variables resolve in the collection chip.** It matched against the
  merged by-name map only, so `{{aspire:demo-api}}` never resolved and the chip showed the raw
  template. The provider- and alias-aware parsing that `VariableInput` already had is now
  shared by both, which repairs the same bare-name bug in `VariableInput`'s own preview toggle.

- **The Content-Type row appears only when the request has one**, instead of on every request
  including a bodyless `DELETE`, where it was a permanently empty field advertising a header
  that is never sent. When hidden, the header list owns Content-Type like any other header.

- **The TLS report offers the certificates.** Per-certificate and whole-chain PEM downloads —
  public material by definition, it is what the handshake hands every client — rather than
  sending you back to `openssl s_client` for bytes the connection you just made already saw.

## Upgrading

Nothing to migrate. No workspace-format or CLI breaking changes, and no API shape changed.

The sidecar handshake gained two error phases (`webroot.missing`, `webroot.empty`) and one
progress phase (`webroot.resolved`). Unknown events have always been logged and ignored, so an
older shell reading a newer sidecar is unaffected. The handshake is only enabled under the
desktop shell, so Docker and Aspire runs — where an empty `wwwroot` is legitimate, because Vite
is serving the UI separately — behave exactly as before.

`.md` workspace files still load with a `W_LEGACY_EXTENSION` warning for the whole 0.7.x line;
`tap-studio migrate` converts a workspace when you're ready. Removal is still targeted at 0.8.0.
