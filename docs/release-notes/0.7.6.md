# Tap 0.7.6 Release Notes

The Windows white screen, found and fixed. 0.7.5 shipped the instruments; this is what they
caught on the first run.

## `\\?\`

Tauri resolves bundled resources relative to `current_exe()`, which it *canonicalizes* — a
deliberate security measure, to resolve symlinks before trusting the path. On Windows,
canonicalization returns a **verbatim** path: `\\?\C:\Users\…\binaries\wwwroot`.

Verbatim paths are passed to Win32 without normalization. The consequence that matters is a
small one: inside a verbatim path, a forward slash is an ordinary filename character rather
than a directory separator.

ASP.NET's `PhysicalFileProvider` joins its root to the request's own `/`-separated subpath and
hands the result to the filesystem. Under a `\\?\` root, that makes every **nested** request ask
for a file whose name literally contains a slash:

```
GET /tap-studio-icon.svg              → 200   (one segment, no slash to mistranslate)
GET /assets/index-B2qhevLj.js         → 404   (two segments)
GET /assets/index-D5hl7OH6.css        → 404
```

`index.html` sits at the root of `wwwroot`, so it was served perfectly. Its stylesheet and its
entire script bundle live under `assets/`, so neither existed as far as the server was
concerned. The webview received a valid HTML document containing an empty `<div id="root">`,
had nothing to run, and painted white — which is exactly what it was told to do.

The prefix is now stripped before the path leaves the shell, and stripped again defensively in
`StudioHost`, which is the layer that knows the file provider is sensitive to it. Only the plain
drive form is unwrapped: `\\?\UNC\server\share` is not a usable path without its prefix, and a
path long enough to have genuinely needed one is not a path to quietly shorten.

This was never a WebView2 problem, a GPU problem, or a virtualization problem. It was a string.

## The diagnosis reached the log and not the screen

0.7.5's blank-page watchdog worked. It caught the failure, named the file, and wrote it down:

```
webview loading about:blank#tapfail=script%20error%20%7C%20failed%20to%20load%20…index-B2qhevLj.js
```

And then handed the window to `about:blank`, which is white.

The shell reads its splash address from the window at startup so it always has somewhere to
return to. On macOS that window has already navigated by then. On Windows it has not — it is
still on `about:blank` for another eighty milliseconds — so the address the shell memorised as
"home" was a blank page. The user got a white screen either way, and the only sign anything had
been diagnosed was a fragment on a URL they could not see.

`about:blank` is now refused as a splash address, and the real one is learned from the first
page the shell actually serves, whatever scheme the platform gives it. That still lands two and
a half seconds before the sidecar is ready.

## The failure card follows the evidence

A page that loads and renders nothing has two unrelated causes, and 0.7.5 confidently named the
wrong one — it blamed an out-of-date WebView2 runtime in both cases. A subresource that failed
to load is the *server* not serving it, which means the install, not the browser engine. Script
that ran and threw is the engine's business. The card now distinguishes them and points at the
one the log supports.

## Upgrading

Nothing to migrate. No workspace-format, CLI, or API changes.

**If you are on Windows and 0.7.4 or 0.7.5 opened to a blank window, this is the release that
fixes it.** Install it over the top; nothing needs uninstalling first. The in-app updater cannot
rescue a blank window — the update check is invoked from the workbench page, which never
rendered — so this one has to be installed by hand. Afterwards, updates work normally again.

`.md` workspace files still load with a `W_LEGACY_EXTENSION` warning for the whole 0.7.x line;
`tap-studio migrate` converts a workspace when you're ready. Removal is still targeted at 0.8.0.
